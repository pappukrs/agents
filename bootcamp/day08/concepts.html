2 · Read the problem

Find four things before you think about code

Most hackathon failures are building the wrong thing well. Every problem statement has the same four parts. Find all of them, and ask the organizers about any that are missing.

InputsWhat does the agent receive? Files, a question, an API, a CSV? How big? What format?
OutputsWhat must it produce? Text, JSON, a file, an action? Is there an exact format?
ScoringHidden test cases? Demo? Code review? Accuracy, speed, cost? This decides where your hours go.
ConstraintsAllowed models, time limits, no internet, rate limits, things the agent must never do.
Practice on a made-up example

"Build an agent that takes a folder of customer emails (.txt, up to 200 files) and produces a JSON report: top 5 complaint themes, each with a count and 2 example email IDs. Submissions are scored on hidden email sets: theme accuracy (60%), valid JSON (20%), live demo (20%). Must finish in under 2 minutes per folder. Only the provided API key may be used."

What the scoring line tells you hereValid JSON is 20% of the score and costs almost nothing: Pydantic + generate_structured (Day 1). Theme accuracy is 60%: spend most hours there, measured with evals. The demo is 20%: a simple Streamlit page is enough. A fancy multi-agent setup earns nothing extra.
Questions to ask in the first 10 minutes"Is the output format exact?" · "Are the hidden tests like the examples?" · "Can we use our own templates?" · "What happens if the agent times out?" Ask them early, while the answers can still change your plan.

4 · Pick an architecture

  
Choose the simplest design that solves the problem

  
Answer the five questions. The picker scores the four designs you practised this week. The default is almost always the top one.

  

    

      

        
Does the answer depend on a pile of documents too big for one prompt?

        
Does it need to take actions or compute (APIs, files, math, data)?

        
Are there several independent sub-tasks that could run in parallel?

        
Does a human need to approve steps, or must runs resume after a crash?

        
Is speed or cost part of the score?

      

      

        
Single agent + tools 
Day 2 loop. Fewest moving parts, easy to debug and to explain. The default.

        
Agent + RAG tool 
Day 3. Same loop with a search_docs tool. Use when answers live in documents.

        
Multi-agent (planner / workers / reviewer) 
Day 4. Only when sub-tasks really are independent, and you measured that it helps. Slower and costlier.

        
LangGraph 
Day 5. Use when you need branching state, human approval or checkpoints. Otherwise it's extra setup time.

        
Answer the questions to see a recommendation.

      

    

  

  
JS analogyIt's like picking Express vs a microservices mesh for a weekend project. Start with the monolith. You can add a RAG tool or a reviewer step later in 30 minutes. Taking a five-agent design apart at hour 3 is very hard.






  
5 · Drive Claude Code well

  
Small, specific tasks. Review every diff.

  
AI tools are allowed for everyone, so the edge is in how you use them. Big vague prompts give big vague diffs you can't check in time.

  

    
Vague
Build the email agent from the problem
statement. Make it good and add a UI.

    
Specific
Read SPEC.md. In agent/tools.py add a @tool
read_email(email_id: str) -> str that reads
data/emails/{email_id}.txt via safe_path.
Add tests in tests/test_tools.py: reads a
real file; "../x" returns an error. Don't
change loop.py. Run pytest and show output.

  

  

    
Vague
It's not working, fix it.

    
Specific
Case e07 in evals/cases.jsonl fails: expected
theme "refund delay", got "billing". Trace in
traces/run-...json shows search_docs returned
0 hits for "refund". Find why and propose a
fix before editing.

  

  

    
RuleWhy

    
One task per prompt: a file, a function, a testA diff you can read in 1 minute is a diff you can trust

    
Name the files, the signature and the testStops the AI from inventing structure or touching unrelated code

    
Say what NOT to change"Don't change loop.py" protects the parts that already work

    
Paste evidence for bugs (trace, error, case id)The AI debugs from facts, not guesses

    
Run tests after every diff, then commitEach commit is a safe point to go back to

  






  
6 · Commit cadence

  
Commit every 30 minutes, even if it's ugly

  
A commit is an undo point. When a big AI diff breaks things at 2:40, you go back to 2:30, not to 0:30.

  

    Good: a commit every 30 min
    

    Risky: one commit at the end
    

  


# a 10-second habit, set a phone alarm for every :00 and :30
git add -A && git commit -m "1:30 end-to-end CLI answer works"

# something broke and you don't know why?
git diff              # what changed since the last good point
git stash             # park it, get the working version back, demo still works

11 · Self-check

  
Answer out loud before opening

  
What four things do you find in a problem statement before writing code?Inputs, outputs (exact format), how it's scored, and constraints. If one is missing, ask the organizers in the first 10 minutes.

  
Why spend 30 minutes with no code?Building the wrong thing is the most expensive mistake. SPEC.md also becomes the context for every Claude Code prompt, so the 30 minutes come back many times over.

  
What's the default architecture, and when would you leave it?A single agent + tools. Add a RAG tool if answers live in documents. Use LangGraph only for human approval, branching state or resume. Use multi-agent only for really independent sub-tasks you've measured.

  
What makes a good Claude Code prompt?One small task, the files and signature named, what not to change, a test to add, and "run the tests". For bugs, paste the evidence: trace, case id, error.

  
Why commit every 30 minutes?Each commit is a safe undo point. When a diff breaks things, you lose at most 30 minutes, and you always have a demo-able version.

  
By when should you have the first end-to-end answer?Around 1:30. One tool, the starter loop, one case answered in the CLI. Everything after that improves something that already works.

  
What do you do from 4:30 to 5:00?No new features. README (problem, architecture, how to run, eval table, limits), demo script, one rehearsal.

  
What's the most important thing to do after the mock?Fix starter/ with what was missing, not polish the mock project. Tomorrow the starter gets frozen.
