JS analogy for the wheelhouseIt's like running npm ci from a pre-filled offline cache (npm ci --offline). pip download fills the cache; --no-index --find-links wheels/ tells pip "don't go to PyPI, use only this folder".

3 · When the demo breaks

Have a plan for each kind of failure, before you need it

Live demos fail: Wi-Fi drops, the API returns 429, the model says something odd. Decide now what you'll do, so you don't freeze on stage. Click each step.

1
Fallback provider — API down or rate-limited
Your llm.py has a provider switch (Day 7). Set PROVIDER=openai (or anthropic) in .env and re-run. Practise this switch once today, so you know it takes under 30 seconds.
2
Cached responses — slow or flaky network
Run the demo questions once beforehand and save the results (or the trace JSON files). Add a --replay traces/demo.json mode that shows the saved steps. Say clearly "this is a recorded run" if you use it. Honesty scores better than pretending.
3
Recorded backup video — laptop or projector trouble
A 60-second screen recording of a good run, saved locally and on your phone. If nothing else works, play it and talk over it.
4
Explain the trace — the model gives a wrong answer live
Don't hide it. Open the trace panel: "Here it called search_docs, got a low score, and still answered. My eval caught this kind of case: 8/10 pass, here are the two misses." A failure you can explain shows you understand your system.
4 · What judges look for

Score yourself honestly, the way a judge would

The exact rubric isn't known yet (ask on the day), but agent hackathons usually reward these four things. Rate your mock-challenge build. The bars show where to spend your last hour tomorrow.

scores well
  • One agent, a few good tools, clearly explained
  • A scorecard: "9/10 cases pass, avg 2.1 s, 3k tokens"
  • Visible trace of tool steps in the UI
  • "It fails when … ; next I would …"
scores badly
  • 5 agents where 1 would do, no reason given
  • "It works, trust me" with one happy-path demo
  • A crash or stack trace on stage
  • Claiming it handles everything

9 · Self-check

Answer out loud before opening

What are the 5 parts of the pitch, in order?Problem → architecture → demo → eval results → limits. About 20 / 35 / 60 / 40 / 25 seconds.
Why run the fresh-clone test on the laptop you're taking, not your usual machine?Your usual machine has hidden state: a global package, a cached login, an env var. The fresh clone on the real laptop shows what's actually missing.
What do --no-index and --find-links wheels/ do?--no-index: don't contact PyPI. --find-links wheels/: look for packages in this folder. Together they install with no internet.
The Gemini API starts returning 429 during your demo. What do you do?Switch provider in .env (practised, under 30 s). If that fails, use the cached/replay run and say it's recorded. Last resort: the backup video.
The model gives a wrong answer live. What's the best response?Show the trace, explain why it went wrong, and point to the eval numbers that already measure this failure. Explaining a failure shows understanding.
Why is "limits" a part of the pitch at all?Judges know every system has limits. Saying them shows you tested it properly; hiding them makes them doubt everything else.
It's 12:30 and nothing runs end to end. What now?Cut scope: fewer tools, no UI, hard-code a step if needed, until one input goes all the way to one output. Then build up again.
It's 16:15 and you have a great idea for a new feature. What do you do?Write it in the README under "Next steps" and keep going with README, diagram and demo rehearsal. Last hour: no new features.
