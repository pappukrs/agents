2 · What "multi-agent" means

Several small agents instead of one big one

Each "agent" is the same run_agent() loop from Day 2 with a different system prompt, a different tool list, or both. Your Python code decides who runs when.

Single agent (Day 2)

↓
one loop, all tools

Simple, cheap, one trace to debug. Struggles when the job has many independent parts or needs a second opinion.

Multi-agent (today)

↓
worker 1
worker 2
worker 3
↓
writermerges findings
↓
reviewerchecks against sources

Faster when the parts are independent (they run at the same time). Costs more calls and more tokens.

One sentence to rememberMulti-agent is an architecture choice in your Python code, not a model feature. The model doesn't know other agents exist; it only sees the prompt you give it.

Use when the question has parts that don't depend on each other ("revenue by region" + "what customers complained about"). Cost: 1 planner + N workers + 1 writer call. Win: wall-clock time ≈ the slowest worker, not the sum.

Use when each step needs the previous step's output and the steps need very different prompts. Cost: latency is the sum of all steps. Often a single agent with good tools does the same job in fewer calls.

↓ picks exactly one
csv agentanalyze_csv, calculator
docs agentsearch_files, read_file
direct answerno tools

Use when requests are very different kinds and each specialist does better with fewer tools and a focused prompt. Cost: 1 extra small call. Risk: a wrong route gives a confident wrong answer, so always keep a fallback.

writer: draft answer
↓
reviewer: Review{ok: bool, issues: list[str]}
↓ ok=False → back to writer with the issues, max once
final answer

Use when mistakes are expensive and checkable ("every number must appear in the sources"). Cost: +1 to +3 calls. Rule: cap the rounds, or writer and reviewer can argue forever.

4 · Sequential vs parallel

Parallel saves wall-clock time, not tokens

LLM calls spend most of their time waiting on the network, so they can overlap. Move the sliders: workers get different random durations, like real calls.

Sequential: for q in subqs: run(q)
Parallel: await asyncio.gather(*tasks)
planner worker writer waiting for a free slot

Tokens are the same either wayRunning 4 workers in parallel bills exactly the same tokens as running them one after another. Parallel only buys time. And if you fire 8 at once on a free-tier key, you get 429s. That's what the concurrency limit is for.

6 · Reviewer, send back once

A second opinion that can only say "fix these"

The reviewer gets the draft and the raw findings, and returns structured output. Press Next to see a round where the draft has a wrong number.

Why structured output?
Review(ok=False, issues=[...]) is something your code can branch on. "Looks mostly fine, but…" isn't.
Why only once?
Each round costs 2 calls, and the gains drop fast. If round 2 still fails, return the draft with the issues attached. Don't loop.

8 · async / await

Same keywords as JS, one big difference: nothing runs until you start the loop

In JS, calling an async function starts it right away and gives you a Promise. In Python, calling an async def gives you a coroutine that does nothing until it's awaited or scheduled.

Python
import asyncio

async def work(q: str) -> str:
    await asyncio.sleep(1)       # non-blocking
    return f"done {q}"

coro = work("a")   # NOT started yet!

async def main():
    print(await work("a"))

asyncio.run(main())  # starts the event loop
JS / TS
async function work(q) {
  await sleep(1000);
  return `done ${q}`;
}

const p = work("a");   // already running

// Node runs the event loop for you;
// top-level await works in ES modules
console.log(await work("a"));
Two classic mistakes1) Forgetting await: you get <coroutine object work> and a "was never awaited" warning. 2) Using time.sleep() inside async def: it blocks every task. Use await asyncio.sleep().
9 · gather = Promise.all

Run many coroutines at once, get results in order

Python
results = await asyncio.gather(
    work("a"), work("b"), work("c"),
)
# ~1s total, results in input order

# from a list: unpack with *
results = await asyncio.gather(*[work(q) for q in subqs])
JS / TS
const results = await Promise.all([
  work("a"), work("b"), work("c"),
]);


const results = await Promise.all(subqs.map(work));
When one task fails
Python
results = await asyncio.gather(*tasks, return_exceptions=True)
for r in results:
    if isinstance(r, Exception):
        ...  # keep going with the others
JS / TS
const results = await Promise.allSettled(tasks);
for (const r of results) {
  if (r.status === "rejected") { ... }
}

Without return_exceptions=True, gather behaves like Promise.all: the first exception is raised and you lose the other results. For workers, we want allSettled behaviour: one failed worker shouldn't kill the whole answer.

10 · The sync SDK, and rate limits

Our run_agent() is blocking. Two ways to run it in parallel.

Day 2's loop calls client.models.generate_content, which blocks. Calling it directly inside async def would freeze everything. Options:

A · asyncio.to_thread (planned, least change)
await asyncio.to_thread(run_agent, q, verbose=False)
Runs the sync function in a worker thread and gives you something awaitable. Reuses Day 2 code untouched.
B · client.aio (native async)
await client.aio.models.generate_content(
    model="gemini-2.5-flash", contents=..., config=...)
The google-genai SDK has an async twin of every call. Cleaner, but you'd need an async copy of chat() and run_agent().
Semaphore = "at most N at a time"
Python
sem = asyncio.Semaphore(3)

async def worker(q):
    async with sem:          # waits if 3 already running
        return await asyncio.to_thread(run_agent, q)

await asyncio.gather(*[worker(q) for q in subqs])
JS / TS
import pLimit from "p-limit";
const limit = pLimit(3);

await Promise.all(
  subqs.map((q) => limit(() => runAgent(q)))
);

async with is like a try/finally that acquires on entry and releases on exit, even if the worker raises. Day 1's retry loop still handles any 429 that slips through.

# planned: research.py, stripped to the idea
async def research(question: str) -> str:
    plan = patterns.plan(question)                          # 1 structured call
    findings = await patterns.run_workers(plan.subquestions)  # gather + Semaphore(3)
    draft = patterns.write(question, findings)
    review = patterns.review(draft, findings)
    if not review.ok:                                      # send back ONCE
        draft = patterns.write(question, findings, fix=review.issues)
    return draft
12 · Self-check

Answer out loud before opening

Does the model know it's part of a multi-agent system?No. Each agent is a separate call with its own prompt. The "system" exists only in your Python orchestration code.
4 workers run in parallel instead of in sequence. What changes: tokens, cost, or wall-clock?Only wall-clock. Tokens and cost are the same; time drops to roughly the slowest worker (plus planner and writer).
Why does the planner return a Pydantic Plan and not free text?Your code has to loop over the sub-questions. A validated list (capped at 4) is something you can iterate safely; free text isn't.
Why cap the reviewer at one send-back?Each round costs 2 more calls and gains drop fast. Writer and reviewer can disagree forever. Bound it like max_steps.
What's the Python equivalent of Promise.allSettled?asyncio.gather(*tasks, return_exceptions=True): exceptions come back as values in the results list.
Why asyncio.to_thread(run_agent, q) and not just run_agent(q) inside async def?run_agent blocks on network calls. Called directly, it blocks the event loop and the workers run one after another. to_thread runs it in a thread so they overlap.
What does Semaphore(3) protect you from?Firing too many calls at once and getting 429 rate-limit errors (especially on a free-tier key). At most 3 workers run; the rest wait their turn.
Hackathon, hour one: single agent or multi-agent?Single agent. Get an end-to-end demo working, run evals, then add a pattern only where the numbers show it helps.
